# COP 606: Coprocessor Patterns

[COP 503](503.md) introduced the high-level coprocessor path: TiDB divides a query into Region-scoped tasks, TiKV reads each Region from a snapshot, and TiDB combines the partial results.

This chapter looks at what those tasks actually read. SQL talks about tables and indexes, while TiKV stores ordered key-value pairs. TiDB bridges the two by encoding rows and index entries as keys.

## From Tables to TiKV Keys

Consider a small `orders` table with an index on `status`:

```text
orders

id     user_id   status    amount
1001   201       paid      80
1002   202       pending   35
1003   201       paid      52
```

Assume that TiDB assigned this table the ID `42` and assigned the `status` index the ID `3`. First, assume `id` is a **clustered primary key**. That means `id` is also the row handle, the value that identifies the row in TiKV.

TiKV does not store a table object. It stores entries shaped roughly like these:

```text
row data

t42_r1001 -> { user_id: 201, status: "paid",    amount: 80 }
t42_r1002 -> { user_id: 202, status: "pending", amount: 35 }
t42_r1003 -> { user_id: 201, status: "paid",    amount: 52 }

status index

t42_i3_paid_1001    -> ...
t42_i3_paid_1003    -> ...
t42_i3_pending_1002 -> ...
```

These are simplified readable forms, not the literal bytes stored by TiKV. The important pieces are:

- `t42` identifies table 42.
- `r` marks a row key; the following value is the row's handle, `id` in this clustered example.
- `i3` marks index 3; it is followed by the indexed value and, for a non-unique index, the row handle.

The row handle distinguishes rows with the same `status`. A unique index does not need to put the handle in its key. It stores the handle in the index value instead:

```text
t42_i4_alice@example.com -> 1001
```

With a **nonclustered primary key**, the row data uses an internal row handle instead. The primary key is stored as a unique index that translates `id` to that handle:

```text
row data

t42_r5001 -> { id: 1001, user_id: 201, status: "paid", amount: 80 }

primary-key index

t42_i1_1001 -> 5001

non-unique status index

t42_i3_paid_5001 -> ...
```

The exact byte encoding has more details, but this shape explains the access pattern. All row keys for `orders` occupy one interval of TiKV's key space. The entries for one index occupy another interval. TiDB turns a table or index access into one or more ranges within those intervals, then splits those ranges at Region boundaries.

## Table Scans and Index Scans

Consider a query that reads a continuous range of row IDs:

```sql
SELECT *
FROM orders
WHERE id >= 1000 AND id < 1100;
```

The relevant row keys form one continuous interval:

```text
[t42_r1000, t42_r1100)
```

Each cop task seeks to the beginning of its Region's portion, then moves forward with `next()` through the row keys. This is a **table range scan**.

Now consider a query whose requested columns are available from the `status` index:

```sql
SELECT id, status
FROM orders
WHERE status = 'paid';
```

If TiDB chooses that index, TiKV seeks to the `paid` part of the index interval and scans its matching entries:

```text
t42_i3_paid_1001
t42_i3_paid_1003
```

The index contains `status` and the row handle, so this query can be answered directly from the index. This is an **index scan**.

## Index Lookup

The same condition can need more work when the query asks for columns not stored in the index:

```sql
SELECT *
FROM orders
WHERE status = 'paid';
```

TiKV first scans the `paid` index entries to find row handles. It then reads the full rows using those handles:

```text
index scan
  t42_i3_paid_1001 -> row handle 1001
  t42_i3_paid_1003 -> row handle 1003
             |
             v
row reads
  seek t42_r1001
  seek t42_r1003
```

This is an **index lookup**. The index portion is still a contiguous scan, but the returned row handles may be far apart. Fetching full rows can therefore require many separate seeks. A query can have a long index scan and still be expensive because it performs many back-to-table row reads.

The optimizer chooses between these patterns from the query, available indexes, and its estimate of how much data each option will read. The main distinction is simple:

```text
continuous key interval -> seek once, then scan with next()
many unrelated row keys -> seek repeatedly
```

## Join Access Patterns

Joins use the same row and index accesses. Consider:

```sql
SELECT o.id, u.name
FROM orders AS o
JOIN users AS u ON o.user_id = u.id
WHERE o.status = 'paid';
```

With an **index join**, TiDB can scan the matching `orders` rows, take each `user_id`, and look up the matching `users` row through its primary key or unique index. TiKV therefore sees an outer scan followed by many inner row or index lookups. Those inner keys may be unrelated, so this pattern can be seek-heavy even when the outer scan is efficient.

With a **hash join**, TiDB reads both inputs as scans, builds a hash table from one input, and probes it with the other. TiKV supplies the table or index scans; TiDB performs the hash-table matching. The access pattern is usually dominated by the two input scans rather than repeated inner lookups.

The optimizer chooses the join strategy from available indexes and its estimate of the input sizes. In either case, the join eventually becomes table ranges, index ranges, or individual row accesses in TiKV.

## How Operators Pull Data

A scan is often only the first step of the pushed-down work. TiDB describes that work as a directed acyclic graph, or **DAG**, of operators. Each operator performs one transformation on the rows from the operator below it.

For a typical path such as `scan -> filter -> aggregate`, the operators pull data from bottom to top:

```text
aggregate pulls from filter
filter pulls from scan
scan reads from the RocksDB snapshot
```

When the aggregate needs more rows, it asks the filter. The filter asks the scan, and the scan reads the next keys from RocksDB. No operator needs to materialize the full input before its parent can make progress.

For `SELECT COUNT(*) FROM orders WHERE status = 'paid'`, the scan supplies rows, the filter keeps the paid rows, and the aggregate produces a count. Each Region task returns a partial count, and TiDB adds those counts together.

The basic execution path is therefore:

```text
TiDB cop request
        |
        v
Raftstore obtains a snapshot
        |
        v
scan row or index keys in one Region
        |
        v
run the requested operators
        |
        v
return a partial result to TiDB
```

The task reads from the snapshot established by Raftstore, so all of its row and index reads use one consistent view of the Region.
