# COP 706: YATP Internals

TiKV represents the work of a cop request as a task and runs it in the unified read pool. The same pool also serves direct storage reads.

The unified read pool is built on [YATP](https://github.com/tikv/yatp), a Rust thread pool and asynchronous task executor. This chapter explains how it runs those tasks.

## Threads, Workers, and Tasks

YATP creates a limited set of long-lived **worker threads**. Each worker repeatedly takes a ready task from a queue and runs it:

```text
ready tasks
    |
    v
YATP queue
    |
    +----> worker thread 1
    +----> worker thread 2
    +----> worker thread 3
```

A **task** is not another thread. It is a piece of application work that can run on any YATP worker. The pool may contain thousands of tasks while using only a small number of worker threads.

For the read pool, a task is represented by a Rust **Future**. A Future represents work that may need to stop and wait before it can finish. YATP is the **executor** that drives the Future forward.

## Polling a Future

A Future does not run by itself. Its executor gives it a turn by calling `poll()` and asks it to make progress. One poll has two possible results:

```rust
enum Poll<T> {
    Ready(T),
    Pending,
}
```

`Ready` means the task has finished. `Pending` means it is waiting for something else to happen.

Suppose a cop task needs a Region snapshot before it can scan RocksDB:

```text
executor polls the cop task
             |
             v
snapshot is not ready
             |
             v
task returns Pending
             |
             v
worker runs another ready task
```

While the Future is pending, its worker can run another ready task.

`poll()` also provides a **waker**. The operation being awaited keeps that waker. When the snapshot becomes available, it calls the waker to mark the task ready again:

```text
snapshot becomes ready
          |
          v
call the task's waker
          |
          v
task becomes ready again
          |
          v
the executor polls it again
```

The next poll continues from the point represented by the Future's internal state. It does not restart the task from the beginning.

## The Task State Machine

YATP records this lifecycle with four internal states:

```text
NOTIFIED -- worker polls --> POLLING -- Ready --> COMPLETED
   ^                          |
   |                        Pending
   |                          v
   +---------- wake -------- IDLE
```

- **`NOTIFIED`** means the task is ready to be polled. It is normally waiting in a queue.
- **`POLLING`** means a worker is currently running its Future.
- **`IDLE`** means the Future returned `Pending` and is waiting to be woken.
- **`COMPLETED`** means the Future returned `Ready` and will not run again.

A wake-up can race with the current poll. If the task is woken while it is still `POLLING`, YATP records that notification so it will not be lost. Depending on other queued work, YATP can poll the task again immediately or schedule it through the queue.

The useful reader-level distinction is:

```text
POLLING   -> occupies a YATP worker
NOTIFIED  -> ready but may be waiting in a queue
IDLE      -> waiting for an event, occupies no worker
```

## Cooperative Scheduling

The operating system can preempt a YATP worker thread. YATP itself, however, cannot interrupt one Future in the middle of a `poll()` call and use that same worker to poll another task.

The Future must return control to YATP. It can finish with `Ready`, wait with `Pending`, or reach an explicit asynchronous yield point.

An `.await` yields only when the awaited Future returns `Pending`. Synchronous work does not yield automatically. A RocksDB iterator call, a blocking file operation, or a long CPU loop keeps the worker occupied until that code returns.

```text
short poll
  task A ---- Pending ----> worker runs task B

long synchronous poll
  task A ------------------------------> returns
              task B waits
```

This is **cooperative scheduling**. Its advantage is that many waiting tasks can share a small number of threads. Its constraint is that a long poll can delay unrelated ready tasks.

YATP's queue can decide which ready task should run next, but it cannot make a running task yield sooner.

## Choosing the Next Task

YATP supports several queueing strategies. They all run the same Future state machine; they differ only in how workers choose among `NOTIFIED` tasks.

### Single-Level Queue

A single-level pool treats ready tasks alike. A task submitted from outside the pool first enters a shared queue. When a worker needs work, it takes a batch into its own local queue and runs that queue first.

An idle worker can take more tasks from the shared queue or steal a batch from another worker's local queue. This **work stealing** keeps one busy queue from leaving another worker idle.

### Multi-Level Queue

A multi-level pool can place explicitly prioritized tasks at a fixed level. For ordinary tasks without a fixed level, it tracks how much execution time each task has accumulated. Short tasks remain in a higher level; tasks that consume more worker time move to lower levels and are selected less frequently.

Lower levels still receive execution opportunities, so long tasks can make progress. The levels do not impose different time-slice lengths: a running Future must still return from `poll()` cooperatively.

### Priority Queue

A priority pool places ready tasks in one global priority order. Workers choose the highest-priority task available. When TiKV resource control is enabled, it assigns priorities to configured workload groups, and YATP uses those priorities when choosing tasks.

In current TiKV, the unified read pool uses the priority queue when resource control is enabled. Without resource control, it uses the multi-level queue. The single-level queue remains YATP's basic work-stealing option.

---

The complete YATP loop is now visible: **enqueue a ready Future, poll it on a worker, and either complete it or wait for its waker to make it ready again**. The queue decides which ready task runs next; the Future decides when the current poll returns.
