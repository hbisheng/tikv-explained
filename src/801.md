# RAFTSTORE 801: Region Merge

[TiKV 201](201.md) introduced Region as the unit of data distribution. When neighboring Regions become small, PD can schedule them to merge so that the cluster does not keep many tiny Raft groups.

A merge has a **source Region** and a **target Region**. The source disappears, and the target expands to cover both key ranges.

PD coordinates the operation. Before requesting a merge, it ensures that the Regions are adjacent and that their peer placement is aligned. In the usual case, every store that hosts a source peer also hosts the corresponding target peer:

```text
Store 1: source peer  | target peer
Store 2: source peer  | target peer
Store 3: source peer  | target peer
```

This alignment lets TiKV merge the Regions without copying their data between stores. The data already exists on the same stores; the operation mainly changes which Region owns the combined range.

The merge has two Raft steps:

```text
source Region: PrepareMerge
target Region: CommitMerge
```

## Prepare the Source

PD sends a `PrepareMerge` request to the source Region's leader. TiKV first checks that the request is still valid and that the source is ready to merge.

The source leader checks how far its peers have replicated the Raft log. For each peer, the leader tracks a **matched index**, the highest log index that the peer is known to have replicated. The leader takes the smallest matched index across the peers:

```text
source leader's last index:  120

peer 1 matched index:         118
peer 2 matched index:         116
peer 3 matched index:         119

minimum matched index:        116
```

The source cannot safely merge if a peer is too far behind. The Raft log entries after the minimum matched index must be available and small enough to carry to the target during the next step. TiKV also rejects the merge when the gap is too large or the interval contains an operation that could change the Region configuration or range.

If these checks pass, the source leader proposes `PrepareMerge` as an admin entry through Raft. The entry is replicated and committed like other Raft entries. When it is applied, every source replica records that it is preparing to merge and stops accepting new writes.

Freezing writes gives the merge a stable boundary. The source's recent history can now be handed to the target without new source writes appearing halfway through the operation.

```text
source Region
      |
      | PrepareMerge commits and applies
      v
source is frozen
      |
      v
source peers prepare the log interval for the target
```

The source keeps the Raft log after the minimum matched index through the committed `PrepareMerge` entry. These entries describe the source state that a lagging source peer may still need to apply before it can disappear.

## Commit the Target

After `PrepareMerge` has applied, the source peer on each store contacts the corresponding target peer. The request contains the source Region information and the necessary Raft log entries.

The target peer must be the **leader** of the target Region to propose the next step. A target follower does not independently commit the merge. Once the target leader accepts the request, it proposes `CommitMerge` to the target Region's Raft group.

`CommitMerge` is therefore committed by the target Raft group, not by the source group:

```text
source peer                  target peer
     |                             |
     | source state and logs       |
     +---------------------------->|
                                   |
                         target leader proposes
                                   |
                                   v
                         target Raft group commits
```

The `CommitMerge` entry carries the source's merge boundary and the source log entries after the minimum matched index. The target needs this information because a source peer may not have applied `PrepareMerge` yet.

## Catch Up the Source

When a target replica applies `CommitMerge`, it first makes sure that the source peer on the same store has caught up to the merge boundary.

If that source peer has already applied `PrepareMerge`, no additional catch-up is needed. If it is behind, the target sends it the carried source log entries. The source appends and applies them in Raft order until it reaches the `PrepareMerge` entry.

```text
target applies CommitMerge
              |
              v
source peer reaches PrepareMerge
              |
              v
source state is ready to be removed
              |
              v
target finishes applying CommitMerge
```

This ordering is important. The source must still exist while its missing history is being applied. If the source were deleted first, the entries needed to finish the merge would be lost.

## Expand the Target Range

After the source peer is caught up, the target can finish applying `CommitMerge`. TiKV updates the target's Region metadata so that its range includes the source range.

For adjacent Regions, the result looks like this:

```text
before:
  source: [a, m)    target: [m, z)

after:
  target: [a, z)
```

The target's Region metadata and the source's removal state are updated together. The source peer and its apply processing can then be destroyed. Because source and target data were already present on the same store, the merge does not need to copy the source key-value data into a new store.

The full flow is:

```text
PD aligns adjacent Regions and their peer placement
                    |
                    v
source leader proposes PrepareMerge
                    |
                    v
source Raft group commits and applies it
                    |
                    v
source writes are frozen
                    |
                    v
target leader proposes CommitMerge
                    |
                    v
target Raft group commits it
                    |
                    v
source peers catch up to the merge boundary
                    |
                    v
target expands its Region range
                    |
                    v
source peers are removed
```

Until `CommitMerge` is committed by the target, the source can still roll back the preparation and resume normal writes. After the target commits it, the merge has passed its point of no return: the target must complete the range update and the source removal.

The durable state transitions and crash-recovery cases behind this process are covered in [RAFTSTORE 901: Raft Peer Lifecycle](901.md). The essential idea is that Region merge changes ownership of an already colocated range, while Raft log catch-up makes sure every source replica reaches the same merge boundary before it disappears.
