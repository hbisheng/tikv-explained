# RAFTSTORE 801: Region Merge

[RAFTSTORE 604](604.md) showed how one Region splits into two. A **Region merge** goes in the opposite direction: it combines two adjacent Regions so that TiKV does not keep many small Raft groups.

Suppose two Regions cover adjacent key ranges:

```text
source Region: [a, m)
target Region: [m, z)
```

After the merge, the source Region disappears. The target Region remains and expands its range:

```text
target Region: [a, z)
```

This looks like a simple metadata change, but source and target are two independent Raft groups. Each has its own leader, log, and apply progress. TiKV cannot place one entry in both logs atomically.

The merge therefore uses two Raft commands:

```text
source Raft group: PrepareMerge
target Raft group: CommitMerge
```

`PrepareMerge` fixes the source history that will be merged. `CommitMerge` makes the target responsible for that history and key range.

## Align the Replicas

PD selects the source and target Regions and coordinates the operation. They must be adjacent, and their peers must be placed on the same TiKV stores before the merge begins.

For example, their placement may initially differ:

```text
source peers: Store 2, Store 3, Store 4
target peers: Store 1, Store 2, Store 3
```

PD first moves the source peer on Store 4 to Store 1 using the replica-movement process from [RAFT 602](602.md). The resulting placement is aligned:

```text
Store 1: source peer | target peer
Store 2: source peer | target peer
Store 3: source peer | target peer
```

This preliminary alignment may move data. Once it is complete, the merge itself needs no cross-store copy of the source key-value data. Every store already holds both adjacent ranges.

## Prepare the Source

PD sends the merge request to the source Region's leader. TiKV verifies that the source and target are still adjacent, their Region metadata is current, and their peers remain aligned.

The source leader must then choose a log boundary that every source peer can reach. For each follower, Raft tracks a **matched index**: the highest log index known to be replicated on that peer.

```text
source leader's last index: 120

peer on Store 1 matched:    120
peer on Store 2 matched:    118
peer on Store 3 matched:    116

minimum matched index:      116
```

Index 116 is known to exist on every source peer. The leader uses the next index, 117, as the beginning of the log interval that may need to be carried through the merge.

TiKV rejects the merge for now if a source peer is too far behind, is receiving a snapshot, or the required log interval is too large. It also rejects an interval containing configuration or other topology-changing commands. Carrying such a history into another Raft group would be unsafe or impractical.

If the checks pass, the source leader proposes `PrepareMerge`. The entry records the target Region and the start of the required log interval. Suppose the entry itself receives index 121:

```text
logs every source peer already has       [ ... 116]
history retained for this merge          [117 ... 121]
                                                    ^
                                             PrepareMerge
```

Once `PrepareMerge` is committed, the source has a fixed endpoint. It no longer accepts ordinary writes. As each source peer applies the entry, it records that the Region is merging.

The source peers do not necessarily reach this point at the same time. Preserving the log interval lets a slower peer catch up later.

## Commit the Target

After a source peer applies `PrepareMerge`, it asks the target peer on the same store to commit the merge. The request carries the source Region metadata and the retained source log entries.

Only the target leader can turn this request into a proposal. It proposes `CommitMerge` in the target Raft group, which replicates and commits the entry like any other Raft command.

```text
source peer on target leader's store
              |
              | source metadata and log entries
              v
        target leader
              |
              | propose CommitMerge
              v
       target Raft group
```

Once the target group commits `CommitMerge`, the merge cannot be rolled back. The target replicas must now complete it on their own stores.

## Catch Up Each Source Peer

A target replica may apply `CommitMerge` before the source peer on the same store has applied `PrepareMerge`. Some committed source entries may therefore be missing from that store's KV state. The target cannot take over the source range until those entries have been applied.

The target therefore pauses its `CommitMerge` application and gives the carried log entries to its local source peer:

```text
target starts applying CommitMerge
                |
                v
has the local source applied PrepareMerge?
                |
        +-------+-------+
        |               |
       yes              no
        |               |
        |        apply the missing source logs
        |               |
        +-------+-------+
                |
                v
stop the source apply path
                |
                v
resume CommitMerge
```

If the source peer has already applied `PrepareMerge`, every earlier source entry has also been applied, so no log replay is needed. Otherwise, it applies the missing entries in source-log order until it reaches `PrepareMerge`.

Only then can the local target finish the merge. TiKV persists two Region metadata changes together:

- The target becomes responsible for the combined range.
- The source is marked as removed.

The target's range update and the source's removal therefore cannot appear as a half-finished pair after a restart. The source peer can then be destroyed.

Because both ranges were already stored on the same TiKV store, the target does not need to rewrite all source key-value pairs. The Region metadata now directs requests for the combined range to the target Raft group.

## Rolling Back

The source may be unable to reach the target because the target changed or became unavailable. As long as the target Raft group has not committed `CommitMerge`, the source group can commit `RollbackMerge` and resume normal writes.

After `CommitMerge` is committed, rollback is no longer possible. Even if a TiKV process crashes at that point, recovery must continue the target range update and source removal.

---

The essential flow is:

```text
align source and target peers
            |
            v
PrepareMerge fixes and freezes the source history
            |
            v
CommitMerge commits the decision in the target group
            |
            v
each local source catches up to the merge boundary
            |
            v
target expands and source disappears
```

This chapter establishes the normal merge path. [RAFTSTORE 901: Raft Peer Lifecycle](901.md) will examine how durable peer states, snapshots, and crash recovery preserve the same result when these steps are interrupted.
