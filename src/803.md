# TXN 803: In-Memory Pessimistic Locks

[TXN 607](607.md) introduced pessimistic transactions. They acquire locks before prewrite so that later writers discover the conflict earlier.

Normally, acquiring a pessimistic lock writes a lock record through Raftstore into the `lock` CF. The record is replicated to the Region's peers and remains there until a later prewrite, rollback, or commit changes it.

An **in-memory pessimistic lock** keeps that lock only in the current leader's memory instead. It avoids a Raft log write and a RocksDB write for the lock-acquisition request.

```text
normal pessimistic lock
  acquire lock -> Raft log -> lock CF

in-memory pessimistic lock
  acquire lock -> current leader's memory
```

This is an optimization. It does not change the transaction's conflict rules. Other operations still have to observe the lock, and a later write still performs the normal MVCC checks described in 607.

## The Leader-Local Lock Table

Each Region peer has an in-memory table of pessimistic locks. Only the current leader accepts new entries into that table.

When a transaction acquires a lock on `account:42`, TiKV records the lock's transaction information in the table:

```text
leader's in-memory lock table

account:42 -> transaction T1 holds a pessimistic lock
```

Another transaction that reads or writes the same key must still see that lock. TiKV's MVCC reader therefore checks the in-memory table before it checks the persistent `lock` CF.

```text
read or write key
      |
      v
check leader's in-memory lock table
      |
      +-- lock found --> handle the conflict
      |
      v
check persistent lock CF
```

The table is tied to a particular Raft term and Region version. If a reader's term or Region version no longer matches the table, TiKV returns a stale-command or epoch error instead of treating a cleared table as proof that no lock exists.

When the peer loses leadership, it clears its table. When it later becomes leader, it starts with an empty writable table for its new term and Region version.

## When TiKV Uses the Fast Path

**Pipelined pessimistic locking** is a related optimization: it can return after a lock request is proposed instead of waiting for it to be fully persisted. In-memory locking requires both the pipelined feature and the in-memory-lock feature to be enabled. For eligible requests, it goes one step further and skips the proposal entirely.

It applies only to eligible pessimistic-lock acquisition requests. Shared locks and requests that must update a shared lock use the normal persistent path instead.

Before inserting a lock, the transaction scheduler checks that:

- the local peer is still the correct leader for the request's term and Region version;
- the in-memory table is writable;
- the lock fits within the configured memory limits.

The current default limits are 512 KiB per Region peer and 100 MiB for the whole TiKV instance. If any check fails, TiKV falls back to the ordinary Raftstore write path.

When the insertion succeeds, the scheduler completes the lock-acquisition request without calling `async_write`. This is the latency benefit: the client does not wait for Raft replication or RocksDB persistence merely to reserve the key.

## Moving a Lock Back to Persistent State

The in-memory lock is not permanent. A later transaction operation can replace or remove it through a normal change to `lock` CF.

For example, when a prewrite turns the earlier reservation into its transaction lock, the scheduler sends the `lock` CF modification through Raftstore. Before it does so, it marks the matching in-memory entry as pending removal. The entry stays in the table until the Raft command applies, then TiKV removes it.

```text
in-memory pessimistic lock
            |
            v
prewrite or rollback changes lock CF through Raft
            |
            v
Raft command applies
            |
            v
remove the in-memory entry
```

Keeping the entry until apply prevents a concurrent operation from treating a change that is only proposed as if it were already complete.

## Why Leader Transfer Needs More Work

An in-memory lock exists on only one peer. A normal leader transfer cannot simply discard it: the target leader would not know that the key is reserved.

Before a voluntary transfer, TiKV converts the live in-memory locks into normal, replicated `lock` CF records. It then uses a second acknowledgement to prove that the target has applied that conversion.

The first part is the ordinary leader-transfer handshake from [RAFT 601](601.md):

```text
old leader
    |
    | MsgTransferLeader
    v
target follower
    |
    | first acknowledgement: applied index
    v
old leader
```

After the old leader accepts the first acknowledgement, it checks its in-memory lock table.

- If the table is empty, it proceeds with the normal leader transfer.
- If the table has live locks, it stops accepting new in-memory locks by putting the table into a transferring state.
- It proposes the live locks as ordinary `Put` operations in `lock` CF.
- It then proposes a special `TransferLeader` admin command after those lock writes.

```text
old leader
    |
    | propose live locks to lock CF
    v
replicated Raft log
    |
    | propose TransferLeader admin command
    v
target follower applies the preceding entries
```

The admin command is an ordering fence. Raft applies entries in order, so when the target applies that command, it has already applied the preceding lock-CF writes.

The target then sends a second `MsgTransferLeader` acknowledgement. This acknowledgement carries a special command-reply context. Only after the old leader receives it does TiKV call `raft-rs` to start the actual Raft leader transfer.

```text
target applies lock records and TransferLeader command
    |
    | second acknowledgement: command reply
    v
old leader
    |
    | RawNode::transfer_leader()
    v
normal Raft leader transfer
```

The new leader can now serve the Region using persistent locks in its local `lock` CF. It does not need the old leader's memory table.

## The Pending-Removal Race

Some in-memory locks may already be on their way out when a leader transfer starts. For example, a prewrite may have submitted a Raft command that changes the lock, but that command has not applied yet.

TiKV marks such an entry as pending removal and does not include it again in the lock-flush command. The already submitted Raft command is responsible for its `lock` CF state. The later `TransferLeader` admin command still provides an ordering boundary: the target cannot send the second acknowledgement until it has applied the earlier command as well.

This avoids reintroducing a lock that a preceding Raft command had already removed or replaced.

## Failed and Unplanned Transfers

While the old leader is flushing the table, new in-memory locks are disabled. If the transfer does not reach the actual Raft handoff, a periodic tick eventually re-enables the table on the still-current leader.

An unexpected leader loss is different from the voluntary path. The old leader clears its in-memory table when it becomes a follower. Those volatile locks are not a durable transaction outcome: no data write has committed because of them. A later transaction operation still goes through the normal MVCC and conflict checks, and the client may need to retry after the leadership change.

The important distinction is:

```text
in-memory lock
  fast, leader-local reservation

persistent lock CF record
  replicated transaction state visible to every peer
```

Leader transfer bridges those two forms before moving the leader role. The same kind of volatile-state handling also matters for Region split and merge; their detailed lifecycle races are deferred to [RAFTSTORE 901](901.md).
