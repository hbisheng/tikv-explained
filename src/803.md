# TXN 803: In-Memory Pessimistic Locks

[TXN 607](607.md) introduced pessimistic transactions. Before changing a key, a transaction can acquire a **pessimistic lock** so that another writer cannot reserve the same key at the same time.

Suppose transaction T1 plans to update `account/42`:

```text
T1 acquires a pessimistic lock on account/42
                         |
                         v
T2 tries to lock account/42 -> conflict
```

The lock is a reservation for a future write. It does not change the account value or make the transaction committed. An ordinary snapshot read can still read the previously committed value.

The normal path stores the reservation in the `lock` CF. Acquiring it therefore requires a Raftstore write:

```text
AcquirePessimisticLock
          |
          v
Raft replication and apply
          |
          v
lock CF
```

This makes the lock durable and available on every replica, but it also puts a Raft and RocksDB write on the critical path of lock acquisition.

An **in-memory pessimistic lock** removes that write for eligible requests. TiKV records the reservation only in the current Region leader's memory and returns the result to TiDB.

```text
AcquirePessimisticLock
          |
          v
leader's in-memory lock table
          |
          v
return success
```

This table is different from the concurrency manager's in-memory locks introduced in [TXN 708](708.md). The concurrency manager covers transaction state while a RocksDB write is in flight. An in-memory pessimistic lock can remain the only copy of a successfully acquired reservation until a later transaction command replaces or removes it.

## Acquiring a Lock

The transaction scheduler first performs the same MVCC checks as the persistent path. When it looks for a lock on a key, it checks the Region leader's in-memory table before reading the `lock` CF:

```text
look up the key's lock
          |
          v
check the in-memory table
          |
          +-- found --> use that lock
          |
          v
check the lock CF
```

This gives transaction commands one logical lock view even though some locks are in memory and others are in RocksDB.

If the lock can be acquired, TiKV tries to insert it into the in-memory table. The table accepts locks only while the local peer is the leader and the request matches its current Raft term and Region version. The term changes with leadership, while the Region version changes after operations such as split or merge.

These checks prevent a request based on stale Region or leadership information from trusting the wrong table. A stale term or Region version causes the request to retry with current routing information. If the table is temporarily non-writable or its memory limit has been reached, lock acquisition falls back to the persistent Raftstore path.

In-memory locking is enabled only together with **pipelined pessimistic locking**. Pipelining can return a persistent lock request after its Raft proposal instead of waiting for apply. In-memory locking goes one step further for an eligible request: it skips the proposal entirely.

## Replacing the In-Memory Lock

The reservation does not remain in memory for the rest of the transaction. A later command normally changes its state through Raftstore.

For example, prewrite replaces the pessimistic reservation with a prewrite lock in the `lock` CF. A pessimistic rollback removes the reservation instead.

```text
in-memory pessimistic lock
            |
            | prewrite or rollback
            v
write the new lock-CF state through Raft
            |
            v
apply the Raft command
            |
            v
remove the in-memory entry
```

Before sending the Raftstore write, TiKV marks the matching in-memory entry as **pending removal**. The entry remains visible until the command applies. Otherwise, another command could observe the lock as absent while its replacement or deletion was only proposed and could still fail.

After apply succeeds, TiKV removes the entry from memory. The persistent state now reflects the result of the prewrite or rollback.

## Losing the Leader

The table belongs to one leader term. If that peer unexpectedly loses leadership, it clears the table. The new leader starts with an empty table for its new term.

This means an in-memory pessimistic lock can be lost during a failure or election. The transaction that acquired it may later fail its prewrite and need to retry because another writer has moved forward.

That outcome is safe because the lost lock was only a reservation. No user-data write was committed by acquiring it. The optimization may increase the chance of a transaction retry, but it cannot turn an uncommitted write into committed data.

A planned leader transfer can do better. TiKV has time to move the reservations into durable storage before changing leaders.

## Leader Transfer

[RAFT 601](601.md) described the normal leader-transfer handshake. The current leader first sends `MsgTransferLeader` to the target follower, which checks its state and returns an acknowledgement containing its applied index.

If the leader has no in-memory pessimistic locks, the normal Raft transfer can begin. Otherwise, TiKV adds another phase.

First, the leader makes its table non-writable. New lock-acquisition requests fall back to the persistent path, so the set being transferred cannot keep changing.

The leader then proposes the live in-memory locks as `Put` operations in the `lock` CF. Locks already marked for removal are excluded because their earlier Raftstore commands are responsible for their final state.

After those writes, TiKV proposes a special `TransferLeader` admin command into the same Raft log:

```text
freeze the in-memory lock table
              |
              v
propose live locks into lock CF
              |
              v
propose TransferLeader admin command
              |
              v
target applies everything in order
```

This admin command does not transfer leadership itself. It is an **apply fence**. Because Raft entries apply in order, the target cannot apply this command until it has applied both the lock writes and any earlier command that was already replacing or removing a lock.

Only the selected target responds when it applies the fence. It sends a second `MsgTransferLeader` acknowledgement, marked as the reply to the admin command:

```text
target applies the TransferLeader fence
              |
              | second acknowledgement
              v
old leader
              |
              | RawNode::transfer_leader()
              v
normal Raft leader transfer
```

The second acknowledgement is the evidence the old leader needs: the target's `lock` CF now contains the transaction state required after the handoff. Only then does TiKV ask `raft-rs` to perform the actual leader transfer.

If the transfer fails before that handoff, the old leader remains leader. After a timeout, TiKV makes its in-memory table writable again and continues serving lock requests.

---

The optimization has two outcomes:

```text
ordinary operation
  acquire in memory -> later transaction command persists or removes the lock

planned leader transfer
  freeze the table -> persist live locks -> receive the second ACK -> transfer
```

An in-memory pessimistic lock avoids replication for a temporary writer reservation. When TiKV needs that reservation to survive a planned leadership change, it first converts the volatile state into ordered, replicated `lock` CF records.
