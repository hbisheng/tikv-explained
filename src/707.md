# COP 707: Coprocessor Execution

[COP 606](606.md) showed how a cop task reads table and index keys and pulls rows through an operator chain. [COP 706](706.md) showed how YATP drives that work by polling a Future on the unified read pool.

This chapter connects the two. We will follow one cop request as it enters the pool, obtains a snapshot, scans RocksDB, yields, and eventually returns a result. We will then map that path to TiKV's execution and storage statistics.

## From Request to Execution

TiKV first parses the cop request and prepares the operator chain described by TiDB. It then submits a Future to the read pool.

Once a YATP worker first polls the Future, the task obtains a Region snapshot. The snapshot may not be ready immediately, so the Future can return `Pending` and resume after Raftstore wakes it.

After the snapshot is ready, TiKV builds a **request handler**, the object that owns the operator chain and produces the response. The handler then pulls rows from its scan operator until it has produced the requested result.

```text
TiDB cop request
       |
       v
parse the request
       |
       v
enter the read pool
       |
       v
obtain a Region snapshot
       |
       v
build the request handler
       |
       v
scan RocksDB and run operators
       |
       v
return the result
```

For a simple unary request, one response finishes the task. A streaming request may produce several response items from the same handler.

## Yielding While Scanning

The scan operator reads RocksDB through synchronous iterator calls. Once one of those calls begins, YATP cannot interrupt it. The cop Future must return control voluntarily before another ready task can use the same worker.

TiKV adds yield checks to its range scanner. The scanner checks the elapsed time after returning the first key from a new range and after every 32 returned keys. If more than 1 ms has elapsed since the scan began or the previous yield, it calls `reschedule().await`:

```text
scan keys
   |
   v
reach a yield check
   |
   +-- no more than 1 ms --> continue scanning
   |
   +-- more than 1 ms ----> yield to YATP
                              |
                              v
                       resume in a later poll
```

The 1 ms value is a target, not a strict upper bound. TiKV checks only after a synchronous RocksDB operation has returned. A slow key lookup or a block read can therefore make one poll run longer before the scanner reaches its next check.

Yielding improves fairness when many tasks are ready. It does not make the scan cheaper: a broad range, many MVCC versions, or expensive RocksDB reads still require the same underlying work. The task may simply spread that work across more YATP polls.

## Admission and Concurrency

A cop request can wait before or during read-pool execution for different reasons.

When resource control is enabled, TiKV first makes an **admission decision** for the request. It may allow the request, delay it, or reject it according to the request's resource group. An admitted request is then placed in the read pool, where its priority affects when YATP selects it.

After execution begins, the cop endpoint has a separate **concurrency limiter** for expensive tasks. A permit is one slot under this limit. A task may run for a short period without one. If it has accumulated more than 5 ms of execution and still has work to do, it must acquire a permit before later polls can continue.

```text
resource-control admission
           |
           v
      read-pool queue
           |
           v
     begin cop work
           |
           +-- finishes quickly --> no permit needed
           |
           +-- still running ----> acquire a concurrency permit
```

Waiting for a permit is asynchronous. The task returns `Pending` and does not occupy a YATP worker while it waits.

These controls protect different boundaries. Resource control decides when workload from a resource group may enter the pool. The read-pool queue decides which ready task gets a worker. The concurrency limiter bounds the number of longer cop tasks that can continue across polls at once.

## Where the Time Goes

TiKV's coprocessor tracker records the request in stages:

```text
task prepared
     |
     | schedule wait
     v
first read-pool poll
     |
     | snapshot wait
     v
snapshot ready
     |
     | handler build
     v
handler execution
     |
     +-- process one poll -- suspend -- process another poll
     |
     v
request complete
```

- **Schedule wait** runs from preparing the task until its first read-pool poll. It can include resource-control admission delay as well as time waiting for a worker.
- **Snapshot wait** runs from that first poll until the Region snapshot is ready.
- **Handler build time** is the time spent constructing the handler and operator chain after obtaining the snapshot.
- **Process time** is the time spent polling the handler Future.
- **Suspend time** is the time between handler polls after the Future has returned `Pending`.

For an ordinary unary request, TiKV sums the process time of all handler polls. Its total wait time includes schedule wait, snapshot wait, and suspension between those polls. Handler build time is reported separately.

A streaming request uses a broader item boundary: each call that produces one response item may itself span multiple Future polls. This distinction matters when reading item-level details, but the same high-level phases still apply.

The unified read-pool panels describe the YATP side of the same execution:

- **Thread Pool Schedule Wait Duration** measures one scheduled run's queue delay. A task that yields and is scheduled again can contribute multiple observations.
- **Duration of One Time Slice** measures one YATP poll.
- **Task Execute Duration** is the accumulated poll execution time of one completed task.
- **Task Schedule Times** is how many times that task was polled before it completed.
- **Running Tasks** counts admitted tasks that have not finished, including tasks that are queued or suspended. It is not a throughput measurement and does not mean that the same number of workers are busy.

The boundaries answer different questions. A long cop schedule wait can come from admission delay or read-pool contention; a long pool schedule wait specifically means a scheduled run waited in the queue. Snapshot wait isolates the period spent obtaining the Region snapshot. Long poll durations mean a task retains a worker for too long before returning control. Many polls mean that the task repeatedly yielded or waited before completion.

## How Much Data Was Read

Timing says where a request spent time. Scan statistics describe how much storage work it performed.

At the TiKV MVCC layer, two fields summarize work in the `write` column family:

- `processed_versions` counts user keys for which the MVCC reader produced a visible result.
- `total_versions` is derived from the number of `get`, `seek`, `seek_for_prev`, `next`, and `prev` operations performed by the `write` CF reader.

Despite their names, these are not two exact counts of physical versions. The second field counts iterator operations. A large gap between them is still useful: it indicates that TiKV performed much more MVCC navigation than the number of useful keys returned.

RocksDB exposes a lower-level view:

- `rocksdb_key_skipped_count` counts internal RocksDB keys skipped while finding the visible entries.
- `rocksdb_delete_skipped_count` counts RocksDB deletion records skipped during that search.

A TiKV MVCC `Delete` record in the `write` CF is still an ordinary RocksDB key-value entry. It does not count as a RocksDB deletion record merely because its MVCC type is `Delete`.

These statistics belong to different layers. The TiKV fields describe MVCC iterator work, while the RocksDB fields describe internal entries hidden by RocksDB's own sequence-number and deletion rules. `rocksdb_key_skipped_count` should not be read as the number of TiKV MVCC versions removed by tombstones.

---

The execution picture is now complete: **a cop request is admitted to the read pool, obtains a Region snapshot, pulls data through its operators, and yields cooperatively while scanning**. Its timing signals show where it waited and ran; its scan statistics show how much MVCC and RocksDB work was required. Together with the access patterns from COP 606, these signals explain why a small SQL result can still produce an expensive cop task.
