# COP 707: Coprocessor Execution

[COP 606](606.md) showed what a cop task does: it reads a Region snapshot, scans row or index keys, and runs pushed-down operators. [COP 706](706.md) explained the cooperative YATP executor that runs read-pool tasks.

This chapter connects those two pictures to performance. A task can wait for a worker, wait for a snapshot, run for one or more time slices, and yield between them.

## One Cop Task's Timeline

The beginning of a request is usually short: TiKV parses it and checks in-memory locks. The task then enters the read pool.

```text
request
  |
  v
wait for a read-pool worker
  |
  v
obtain a Region snapshot
  |
  v
build and run the cop operators
  |
  +-- yield and wait for another poll, when needed
  |
  v
return the result
```

TiKV exposes several timing boundaries for this path:

- `schedule_wait_time`: from task creation until a read-pool worker first runs it.
- `snapshot_wait_time`: from that first poll until snapshot acquisition finishes.
- `handler_build_time`: time to build the cop handler and operator chain.
- `item_process_time`: active time in one poll.
- `item_suspend_time`: time between polls after the task yields.

A task can be polled more than once. Its total wait is not just the first `schedule_wait_time`; it can be scheduled again after every yield.

## Yielding During Scans

YATP is cooperative. A worker cannot interrupt a cop task in the middle of ordinary code, so the task must reach a yield point before another task can use that worker.

RocksDB key scanning is synchronous. `ScanExecutor` normally yields after it completes a range or after it retrieves 32 rows. A slow scan can therefore keep one worker occupied for longer than the configured row count might suggest. If one row takes 10 ms to fetch, a time slice can approach 320 ms.

This is why a task with a small final result can still affect read-pool latency: the cost depends on keys examined and time spent per key, not just bytes returned to TiDB.

## Concurrency and Resource Limits

Before a task reaches the scan, TiKV can limit it in two layers:

```text
resource limiter -> concurrency limiter -> cop scan
```

`server.end-point-max-concurrency` limits concurrent cop work and defaults to the CPU core count. A task that waits at this limit records time in `total_suspend_time` in TiKV logs, rather than ordinary read-pool schedule wait.

Resource control can delay or reject work before the concurrency limiter. These limits are separate from the read-pool queue: a task may wait even when a worker thread is available.

## Reading Cop Metrics

The unified read-pool wait metric records one queue wait: from one enqueue until a worker begins that scheduled run. It is not the task's total waiting time. A task that yields, returns to the queue, and runs again accumulates another wait.

The sampled count of running tasks is also not a throughput measurement. It can rise because many long tasks happen to be active at the sample point, even if every worker is not continuously saturated.

The coprocessor metrics use several higher-level views:

- **Request duration:** wall-clock time from receiving a cop request to completing it.
- **Handle duration:** time spent processing the cop task.
- **Wait time:** `schedule_wait_time` plus `snapshot_wait_time`; it does not include suspension between later polls.

For read-pool throughput, the `count` of task execution-duration observations is more useful than the sampled running-task count.

## Iterator Statistics

TiKV's MVCC statistics usually describe iterator work in the `write` column family:

- `total_process_keys` counts useful keys produced by iterator movement.
- `total_keys` counts iterator operations such as `seek`, `next`, and `prev`.

RocksDB reports a different physical view across all column families:

- `delete_skipped_count` counts RocksDB tombstones skipped by the iterator. A TiKV MVCC `Delete` record is still a normal record for this metric.
- `key_skipped_count` includes ordinary movement past the previously returned key and internal keys hidden by overwrites, deletes, or tombstones.

These counters describe different layers. `key_skipped_count` is not the number of TiKV MVCC versions skipped by tombstones.

When investigating a slow cop request, start with the query's access pattern from [COP 606](606.md): a broad scan, a large index lookup, or many MVCC versions changes the amount and shape of iterator work before any scheduler metric is considered.
