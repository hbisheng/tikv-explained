# TXN 708: Async Commit and 1PC

[TXN 404](404/index.md) introduced the normal two-phase commit path:

```text
prewrite
  store the value and a lock

commit
  remove the lock and write a committed record to write CF
```

The committed record in `write` CF is still necessary. It is the MVCC history that tells later reads when a value became visible.

**Async Commit** and **one-phase commit (1PC)** shorten this path in different ways.

## Async Commit

Async Commit still performs prewrite and leaves a transaction lock in `lock` CF. The lock contains extra Async Commit metadata, including a commit timestamp that can be used to determine the transaction's outcome.

After the async-commit prewrite succeeds, TiDB does not need to send an explicit commit request before reporting success. A later reader or resolver that encounters the lock can determine that the transaction committed and find its commit timestamp from the lock metadata.

The lock is cleaned up and the corresponding `write` CF record is written later. This later work makes the committed version visible through the normal MVCC history.

```text
Async Commit

prewrite
  default CF <- value
  lock CF    <- async-commit lock and commit information
  return success

later
  lock CF    <- remove lock
  write CF   <- committed record
```

The important point is that the remaining lock is enough to figure out the committed result without waiting for a separate explicit commit RPC.

## The Concurrency Manager

Async Commit needs one additional local guarantee. TiKV may report that a prewrite has committed in Raft before its lock has appeared in RocksDB. A reader must not miss the lock during that short interval.

The **concurrency manager** is a TiKV-local component that closes this gap. It keeps two pieces of in-memory state:

- `max_ts`, the largest transaction timestamp observed by this TiKV store;
- an in-memory lock table for prewrites that have not yet reached RocksDB.

When TiKV creates an Async Commit lock, it chooses its minimum commit timestamp to be later than `max_ts`. A read updates `max_ts` before it obtains a RocksDB snapshot. If the read begins first, a later prewrite must choose a commit timestamp after that read:

```text
read at ts 20                 Async Commit prewrite
------------                  ---------------------
update max_ts to 20
                              choose min_commit_ts > 20
                              create the lock
take RocksDB snapshot
```

The read can safely observe the state before that later transaction.

The opposite order needs the lock table. If a prewrite creates its in-memory lock first, a later read checks that table before taking its RocksDB snapshot. It sees the conflicting lock instead of returning data without noticing it.

```text
Async Commit prewrite         read at ts 20
---------------------         ------------
create in-memory lock
                              check the in-memory lock table
                              find the conflicting lock
write lock to lock CF
remove in-memory lock
```

Once the lock is in RocksDB, the normal MVCC read path can find it in `lock` CF. The in-memory copy is no longer needed.

## One-Phase Commit

1PC finishes the transaction in the prewrite request itself. TiKV writes the committed `write` CF record directly instead of leaving a transaction lock for a later commit request.

```text
1PC

one Raft write
  default CF <- value, when needed
  write CF   <- committed record
  no lock CF record remains
```

1PC avoids both the separate commit RPC and the lock left by normal prewrite. TiKV uses it only when the transaction can safely finish in that one phase. Otherwise, it falls back to the normal 2PC path.

For now, keep the distinction simple:

```text
Async Commit: lock remains; write CF can be completed later.
1PC:          no transaction lock remains; write CF is written immediately.
```
