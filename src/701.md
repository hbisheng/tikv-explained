# RAFTSTORE 701: Batch System

[RAFTSTORE 501](501.md) introduced the Raft batch system and the apply batch system. Both let one TiKV store handle many Region peers without turning every small piece of work into a separate I/O operation.

This chapter looks at the scheduling structure behind those two systems. The main idea is simple: each Region keeps its own ordered work, while a shared pool of workers processes many Regions and batches the physical work.

## From a Region ID to a Peer FSM

Every Region peer has a **peer FSM**, the state machine that drives its `raft-rs` instance. A store can host many such peers, so a message first needs to find the right one.

The **Router** is an address book from a Region ID to its **mailbox**. A mailbox has two parts:

- a queue of pending messages for one FSM;
- the FSM itself when no worker is currently handling it.

When a Raft message, local proposal, or tick arrives, the Router finds the mailbox for its Region. The mailbox puts the message into its queue and schedules the FSM for processing.

```text
incoming event
      |
      v
Router: Region ID -> mailbox
      |
      v
mailbox queue
      |
      v
schedule the peer FSM
```

A mailbox schedules an FSM only when that FSM is idle. If a worker already owns it, new messages simply wait in the mailbox queue. This guarantees that two workers do not process the same Region peer at the same time, so the peer's Raft state remains ordered.

When a worker starts processing an FSM, it temporarily takes ownership of it from the mailbox. When the work for that turn is finished, it releases the FSM back to the mailbox. In the code, these ownership transfers are `take_fsm()` and `release()`.

## Pollers and Batches

The batch system has several worker threads called **pollers**. They share a queue of scheduled FSMs. A poller takes scheduled FSMs from that queue and lets the appropriate Raftstore handler process their pending messages.

One pass over a group of FSMs is a **batch round**. The default maximum batch size is 256 FSMs. A poller processes each FSM in its current batch, then adds more scheduled FSMs while the batch is below that limit.

```text
scheduled FSMs
      |
      v
poller
      |
      +--> Region 1 FSM
      +--> Region 2 FSM
      +--> Region 3 FSM
      |
      v
handler processes one round of work for each FSM
```

The limit is a target, not an absolute barrier. At the beginning of a round, a poller fetches a newly scheduled FSM even when its existing batch is already full. This gives newly active Regions a chance to run instead of letting a fixed batch monopolize the worker.

A hot FSM can remain in a poller's batch across several rounds. To keep other Regions from waiting forever, the batch system watches how long an FSM has stayed there. After the default five-second reschedule period, it reschedules about half of the hot FSMs. The next poller round can then mix in other work.

This scheduling mechanism is shared by the Raft and apply paths. What their handlers do is different.

## The Raft Batch System

The Raft batch system handles peer FSMs. For one peer, its normal handler takes messages from the mailbox and feeds them into the peer's Raft event loop.

One turn handles at most `messages-per-tick` messages for that peer, 4,096 by default. That bound prevents one peer with a large queue from keeping a poller forever. The messages may include incoming Raft messages, local proposals, and internal tick events.

As described in [RAFTSTORE 402](402.md), these events drive `raft-rs`. The resulting `Ready` can contain Raft log entries to persist, outgoing Raft messages, and committed entries to apply.

The important batching boundary appears after several peers have been processed:

```text
Region 1 Ready ---\
Region 2 Ready ----> batch Raft Engine writes and outgoing messages
Region 3 Ready ---/
                         |
                         v
                    committed entries
                         |
                         v
                 send to the apply batch system
```

Each peer still has its own Raft log and ordering. Raftstore batches only the physical work that is independent across peers.

The **Process Ready Duration** metric measures the time spent handling a Raft poller's batch round when that round contains `Ready` work. If it rises, the Raftstore processing path is slow. Raft Engine I/O can be one cause, but the metric covers the whole batch-handling path, so it is a starting signal rather than proof of one specific bottleneck.

## The Apply Batch System

Committed entries move from the Raft batch system to one **ApplyFsm** per Region. An ApplyFsm interprets its Region's committed entries in log order and produces changes for the KV Engine, such as writing a key, deleting a key, or advancing the apply index.

The apply batch system uses the same general model:

```text
committed entries for many Regions
              |
              v
          ApplyFsms
              |
              v
one larger KV Engine write batch
```

The apply path has an additional fairness mechanism. As an ApplyFsm processes entries, it accumulates KV Engine writes. After it flushes enough data, it can **yield**: it stops for the current turn and lets the poller continue with other work. The `apply-yield-write-size` setting controls this threshold. Its default is 32 KiB. TiKV also has a time-based yield limit.

Yielding is useful when one Region is hot. Without it, a large apply backlog from that Region could keep an apply worker occupied for too long. The tradeoff is that the hot Region may need several turns to finish its backlog. Between turns, its remaining entries can wait behind other runnable ApplyFsms.

## Reading Apply Delay

Two measurements answer different questions:

- **apply log** measures work after the apply path starts processing a committed entry;
- **apply wait** measures how long an apply request waited before an ApplyFsm started handling it.

If apply log is normal but apply wait is high, the immediate problem is queueing rather than the cost of one individual apply operation. The apply workers may already be busy with other Regions, or a hot Region may repeatedly yield and wait for later turns. KV Engine pressure can still be the underlying cause when it keeps workers occupied.

Increasing the apply-worker pool can help only when there is independent Region work that additional workers can process. It cannot make one Region apply entries in parallel, because that Region must preserve Raft log order.

Likewise, `store-max-batch-size` and `apply-max-batch-size` control how many FSMs a poller can keep in one batch; they do not make a single hot FSM faster. Reaching either limit is not, by itself, evidence that the limit should be raised. A larger batch can reduce scheduling overhead for many active Regions, but it can also make fairness and tail latency worse.

The useful mental model is:

```text
many independent Regions
        |
        v
batch system shares pollers and I/O efficiently
        |
        v
each Region still advances its own Raft and apply state in order
```

This is how Raftstore turns many single-Region event loops into one efficient store-wide system. Later chapters build on this picture when examining slow-score probes, Region workers, and peer lifecycle details.
