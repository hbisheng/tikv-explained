# RAFTSTORE 703: Region Worker

The **Region worker** handles background work related to a Region's local data. At a high level, it has three responsibilities:

1. generate Raft snapshots;
2. apply Raft snapshots;
3. delete data that no longer belongs to a live Region.

[RAFT 603: Raft Snapshot](603.md) introduced snapshot generation and transfer at the protocol level. This chapter focuses on the local storage work behind snapshot application and Region deletion. These two operations are closely related because applying a snapshot may need to remove old Region data first.

## Snapshot Generation

Snapshot generation reads a Region's current key-value state and builds the SST files that another peer can ingest. It is expensive because it scans the Region and creates a potentially large amount of data.

The Region worker runs this work outside the normal Raft event loop. A long snapshot operation should not prevent the Region peer from processing ordinary Raft messages. The leader can then continue serving the Raft group while the snapshot is being prepared, and `raft-rs` can retry the request until the snapshot is ready.

The generation flow is:

```text
Raftstore needs a snapshot
          |
          v
read the Region from RocksDB
          |
          v
write the Region data into SST files
          |
          v
make the snapshot available for transfer
```

The snapshot's data represents one Region state at a known Raft index. The details of that index and its transfer are covered in 603.

## Snapshot Application and Cleanup

When a new peer receives a snapshot, the Region worker must install the snapshot data into RocksDB. The target key range may already contain data from an old peer or from an earlier failed operation. Applying the new SST files without cleaning that data first could leave conflicting versions in the local engine.

There is also a metadata requirement: no **valid Region metadata** may overlap the range being installed. Two valid Regions cannot claim the same key range on one store. If overlapping metadata still exists, the snapshot cannot be safely applied until the conflict is resolved.

The high-level apply flow is:

```text
receive snapshot metadata and SST files
          |
          v
check for overlapping valid Regions
          |
          v
clean old data in the snapshot range
          |
          v
ingest the snapshot SST files into RocksDB
          |
          v
persist the completed Region state
```

Here, **ingest** means adding external SST files to RocksDB as part of the Region's local data. It is much faster than reading every key from the files and writing the keys one by one.

The cleanup step must handle both data and metadata. The Region metadata identifies the range that the new peer should own. The local RocksDB may still contain physical data for a stale peer that used to own that range. The worker removes that stale data before installing the new state.

After the snapshot is installed, the peer's local state reflects the snapshot index. The leader can then resume ordinary log replication with entries after that index.

## Deleting a Region Safely

Deleting a Region does not always mean deleting its data immediately. A read may already be using a RocksDB snapshot created before the Region was removed. That snapshot can still need to see the old data.

When a Region is destroyed, the Region worker records its key range and the current RocksDB sequence number. It postpones the physical deletion:

```text
Region is removed
          |
          v
record its key range and deletion sequence
          |
          v
wait for older RocksDB snapshots to disappear
          |
          v
delete the stale data
```

RocksDB exposes the oldest sequence number still held by an active snapshot. Once that number has moved past the sequence recorded for the deleted Region, no active reader can still depend on the old Region data. The Region worker can then delete it without breaking a reader's consistent view.

This delay is particularly important for coprocessor requests and range scans. A scan can keep a snapshot alive while the Region metadata has already moved elsewhere.

## Choosing a Deletion Method

The most efficient cleanup is to delete whole SST files when the files are wholly contained in the obsolete Region range. Removing the files directly avoids visiting every key:

```text
SST file range:       [a, h)
obsolete Region:      [a, h)

delete the SST file directly
```

When an SST file crosses the boundary of the range being deleted, TiKV cannot remove the entire file. It must remove the keys belonging to the obsolete range while preserving keys outside it. At a conceptual level, this means deleting by key rather than deleting the file.

TiKV once used a special deletion-SST technique for some of these cases: it generated an SST containing deletion entries and ingested that file. This legacy approach is no longer preferred. Direct file deletion is better when the range fully contains the files, and key-based deletion is safer when the files contain data that must be preserved.

The choice can therefore be summarized as:

```text
obsolete range fully contains SST files
    -> delete files directly

SST files cross the range boundary
    -> delete the matching keys

legacy fallback
    -> ingest deletion SST files
```

## One Worker, One Safety Boundary

Snapshot application and Region deletion are not independent cleanup jobs. Both change the physical contents of RocksDB while readers may still hold snapshots and while Region metadata is changing.

The Region worker coordinates the boundary:

- snapshot application waits for a valid, non-overlapping Region range;
- Region deletion waits for readers that may still reference the old range;
- cleanup chooses file deletion or key deletion according to the SST boundaries;
- only then does TiKV install or remove the Region's local data.

This is the storage-side reason that snapshot application and Region deletion belong in the same worker. The more detailed crash-recovery states and races with split, merge, and peer creation are covered in [RAFTSTORE 901: Raft Peer Lifecycle](901.md).
