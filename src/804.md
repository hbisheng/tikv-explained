# ROCKSDB 804: GC and Compaction Filter

[TXN 404](404/index.md) introduced TiKV's MVCC history: a key can have several committed versions in the `write` and `default` column families. Old versions are necessary for old snapshots, but retaining every version forever would make the database and its compactions grow without bound.

## GC Lifetime and the Safe Point

TiDB's **GC lifetime** defines how much historical data the system tries to retain. From that lifetime, TiDB advances a cluster-wide timestamp called the **GC safe point**.

The safe point defines the boundary of supported history:

```text
read_ts < safe point   -> no longer guaranteed to read old history
read_ts >= safe point  -> must still return a correct result
```

This makes old MVCC versions eligible for reclamation, but it does not mean that every version before the safe point can disappear. TiKV must keep the newest committed version at or before the safe point. A read exactly at the safe point may need that version.

For example:

```text
write CF for key k

commit_ts 80 -> Put, value C
commit_ts 50 -> Put, value B   <- keep for safe_point = 60
commit_ts 20 -> Put, value A   <- can be removed
```

A read at timestamp 60 must still return `B`. The version at 50 is the boundary version; the older version at 20 is no longer needed. For a large value, removing its `write` CF record also allows TiKV to remove the corresponding value in `default` CF.

The GC lifetime is therefore a history-retention policy. It determines how far the safe point can advance; the safe point determines which versions can be reclaimed.

## Resolve Old Locks First

A lock represents a transaction that has started writing but has not reached a final committed or rolled-back state. TiKV cannot safely discard old history while such a transaction remains unresolved.

Before publishing a new GC safe point, TiDB resolves locks whose transaction timestamps are older than the boundary. It checks the transaction outcome and either commits or rolls back the lock.

```text
advance transaction safe point
            |
            v
resolve older locks
            |
            v
publish GC safe point
            |
            v
reclaim obsolete MVCC versions
```

After this process, transactions older than the safe point cannot continue, and TiKV can clean versions that no supported snapshot needs.

## Traditional GC

The direct GC path scans the keys in a Region. For each key, it reads the version chain in `write` CF and decides which records are still needed at the safe point.

When it removes an old `Put` record, it performs two related deletions:

```text
write CF:   delete (key, commit_ts)
default CF: delete (key, start_ts)   if the value is stored there
```

Small values may be embedded directly in the `write` record, so they have no corresponding `default` CF value to delete.

The GC worker collects the `write` and `default` CF deletions in the same GC write batch. It does not first delete the write record and later delete the value. The two deletions are submitted together.

```text
scan Region keys
        |
        v
find versions older than the retained boundary
        |
        v
build write-CF and default-CF deletions
        |
        v
submit one GC write batch
```

This path gives GC direct coverage of the Region, but it must scan version chains and issue extra writes just to remove data.

## GC During Compaction

RocksDB compaction already reads and rewrites `write` CF SST files. A **compaction filter** can examine each `write` record during that work and drop records that the safe point no longer needs.

For one key, the filter keeps records newer than the safe point. It also keeps the first `Put` or `Delete` record at or below the safe point, because that record defines what a read at the safe point should observe. Older records can be removed.

```text
write CF for key k, safe_point = 60

80 -> Put C       keep: newer than safe point
50 -> Put B       keep: boundary version
20 -> Put A       remove: older history
```

When the filter removes an old `Put` record whose value is in `default` CF, it records a matching `default` CF deletion in a separate write batch. The filter must not drop the reference while leaving the old value behind forever.

This reuses I/O that compaction was already performing. The cleanup is opportunistic, however: a version is considered only when its SST file participates in compaction. Traditional GC scans a Region deliberately; the filter cleans data as RocksDB reorganizes files.

## Why Deletes Reach the Bottom Level

`Delete` here means TiKV's MVCC delete record, not a RocksDB deletion marker. A delete record may be the newest version at or before the safe point:

```text
commit_ts 50 -> Delete   <- a read at safe point 60 must see no key
commit_ts 20 -> Put A
```

The delete cannot be removed while lower LSM levels may still contain the older `Put`. Otherwise, a later compaction could expose `A` again. The delete must remain until it reaches the **bottommost level**, where RocksDB knows there are no deeper files containing an older version.

At that point, TiKV can remove the delete record. The GC path also cleans any remaining old `default` CF values that those obsolete write records referenced.

```text
Delete record reaches bottommost level
              |
              v
no older version can exist below it
              |
              v
remove the delete and reclaim old default-CF values
```

The essential distinction is simple: the GC safe point decides which history is logically unnecessary; traditional GC and the compaction filter are two physical ways to remove it. The first scans keys directly. The second cleans records while RocksDB is already compacting them.
