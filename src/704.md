# ROCKSDB 704: Titan

[ROCKSDB 605](605.md) showed that RocksDB stores flushed data in SST files and repeatedly rewrites those files during compaction. This works well for ordinary values, but large values make every rewrite expensive.

## The Cost of Large Values

In an LSM tree, a value can be written several times:

```text
memtable -> flush -> L0 -> compaction -> L1 -> ... -> deeper levels
```

There is no fixed number of rewrites. It depends on the compaction strategy, the database size, the workload, and how long the value remains live. A value that stays unchanged may be rewritten as it moves through levels. A frequently updated value may create even more work.

For a small value, this extra I/O may be acceptable. For a large value, every rewrite reads and writes a large amount of data. This increases **write amplification** and also consumes the I/O bandwidth needed by foreground reads and writes.

## Separate Values from the LSM Tree

Titan is TiKV's value-separation engine. It keeps large values outside the normal LSM files and leaves a small reference in the LSM tree.

Values below a configured threshold remain in the normal RocksDB path. When a value is larger than `min-blob-size`, Titan writes the value to a **blob file** and stores a **BlobIndex** in the LSM tree. The BlobIndex identifies where the value is stored.

```text
key: user:42:profile

normal value:
  LSM entry -> the value itself

large value:
  LSM entry -> BlobIndex(file, offset, length)
                         |
                         v
                    blob file -> large value
```

The LSM tree still stores and compacts the key. It now rewrites the small BlobIndex instead of rewriting the large value each time. A read follows the BlobIndex to fetch the value from the blob file. Titan can cache blob records, but value separation may add a separate lookup or read compared with an inline value.

`min-blob-size` controls which values are separated. In the current TiKV configuration, the default for newly created databases is 32 KiB. Existing deployments created before TiKV 7.6 may retain the older 1 KiB default.

## Updates Create Discardable Blob Records

Blob files are append-oriented. Titan generally does not edit an old value in place.

Suppose a key is updated twice:

```text
put profile = value-A
put profile = value-B
```

The second write creates a new value and a new LSM reference. After compaction removes the old reference, the record for `value-A` is no longer needed by the current LSM state. Titan marks its space as **discardable**.

A delete works in the same general way, but a deleted key is not necessarily immediately free to remove. TiKV may still retain older MVCC versions, and an active RocksDB snapshot may still need to read them. A blob record becomes reclaimable only after no retained LSM reference needs it.

This is separate from TiKV's MVCC garbage collection. MVCC cleanup removes old transactional versions from the key-value view. Titan reclaims the blob-file space that becomes unused after those references disappear.

## Blob Garbage Collection

Blob files are not useful just because they contain some live values. A file may contain a mixture of live and discardable records:

```text
blob file 17
  live value       40 MiB
  discardable data 60 MiB
  discardable ratio = 60%
```

Titan tracks the amount of discardable data in each blob file. When the ratio exceeds the configured `discardable-ratio`, the file becomes a candidate for **blob GC**. The default threshold is 0.5.

Blob GC is a background operation:

```text
select blob file with enough discardable data
              |
              v
read its remaining live values
              |
              v
write live values to a new blob file
              |
              v
update LSM references
              |
              v
remove the old blob file when no longer referenced
```

The important point is that GC does not simply delete every record marked discardable. Blob files contain variable-sized records, so Titan rewrites the live records elsewhere and then removes the old file when the old references are gone.

TiKV limits the number of background Titan GC jobs. GC therefore competes for some I/O and CPU, but it runs only when reclaiming the space is worthwhile. A very low discardable ratio would cause frequent rewrites for little reclaimed space; a high ratio keeps obsolete data around longer.

## The Tradeoff

Titan changes the shape of the work:

```text
without Titan:
  compaction repeatedly rewrites keys and large values

with Titan:
  compaction repeatedly rewrites keys and small references
  blob GC occasionally rewrites live large values
```

The goal is to reduce the repeated compaction cost of large values, not to eliminate all I/O. The tradeoff is less compaction write amplification in exchange for blob-file reads, blob-file metadata, and occasional blob GC.

That is the basic Titan model: **large values live in blob files, the LSM tree stores references, and background GC reclaims blob-file space after those references become obsolete**.
