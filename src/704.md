# ROCKSDB 704: RocksDB Details

[ROCKSDB 605](605.md) introduced the main LSM tree: WAL, memtables, SST files, levels, and compaction. This chapter looks at several details that matter when reading TiKV code or diagnosing RocksDB behavior.

## Write Pressure and Flow Control

RocksDB turns writes into durable data through several background steps:

```text
write -> memtable -> flush -> L0 SST -> compaction -> deeper levels
```

If the background work cannot keep up, pressure appears at different points in this path:

- **Immutable memtables:** a filled memtable is waiting to flush to an SST file.
- **L0 files:** flushes are creating L0 files faster than compaction can absorb them.
- **Pending compaction bytes:** RocksDB estimates that a large amount of data still needs compaction.

All three mean that accepting writes at the current rate will make the backlog worse.

TiKV handles this through its own write **flow control** at the transaction scheduler. When flow control is enabled, TiKV disables RocksDB's built-in write stall for its column families. This moves the control point before Raftstore and the apply path, where TiKV can slow write traffic more deliberately.

The default pressure thresholds are:

```text
immutable memtables:       5
L0 files:                  20
pending compaction bytes:  192 GiB soft limit, 1 TiB hard limit
```

The first two signals reduce the allowed write rate. TiKV delays write commands at the scheduler until the backlog falls. For pending compaction bytes, TiKV increases a discard ratio between the soft and hard limits, so the scheduler can reject part of the incoming write traffic before the storage engine is overwhelmed.

The exact controller smooths these signals rather than reacting to one instantaneous sample. For now, the main point is that TiKV watches pressure across the whole write path, not only at the memtable.

## Grouping Concurrent Writes

Raftstore's apply path first gathers a Region's key-value changes into a `WriteBatch`. It then submits that batch to RocksDB.

Several threads may submit batches at the same time. RocksDB does not let them append to the WAL independently. Its **WriteThread** chooses one writer as a leader and combines compatible writers into a **write group**.

```text
many WriteBatches
        |
        v
WriteThread queue
        |
        v
leader forms a write group
        |
        +-- append one ordered WAL group
        +-- assign sequence numbers
        +-- insert into memtables
```

The WAL append remains ordered and sequential. When the write group and memtable implementation allow it, RocksDB can insert the group into the memtable in parallel. This preserves one visible write order while using more CPU for the in-memory work.

The size of a write group is limited. TiKV uses a 1 MiB maximum group size by default, so one leader does not hold the path for an unbounded amount of work.

## Prefix Seeks in the Write CF

TiKV's `write` column family stores several MVCC versions of one user key. The versions share the raw user key and differ by a timestamp suffix.

```text
user:42:name | commit_ts 30
user:42:name | commit_ts 20
user:42:name | commit_ts 10
user:43:name | commit_ts 25
```

A point lookup usually needs the version chain for one raw key, not the next user's key. A **prefix seek** lets an iterator stay within that key's version chain.

For `write` CF, the useful prefix is the raw user key with the timestamp suffix removed. If the timestamp remained part of the prefix, each version would look like a different key and the prefix would not group the chain. The same prefix can be used by a Bloom filter to rule out SST files that have no versions of that raw key.

## Choosing a Compaction

[ROCKSDB 605](605.md) described the high-level rule: RocksDB selects a level under pressure, then merges data into the next level. The file selection is more careful than choosing one file at random.

RocksDB starts with a **seed file** and its key range. It expands that range in three directions:

1. It includes adjacent input files that contain other versions of the same user key. This creates a **clean cut**, so one compaction does not split a key's version chain across incompatible boundaries.
2. It includes every file in the output level that overlaps the resulting key range.
3. It may include nearby input files when doing so does not enlarge the output range further.

```text
input level:   [seed][same-key versions]
output level:        [overlap][overlap]
                \_____ compaction range _____/
```

The result is a self-contained merge range: the compaction has every required input and every overlapping output file.

## Compaction Parallelism

Flushes and compactions run as background jobs. Their total concurrency is limited so that background work does not consume the entire machine.

Several compactions can run at once only when their input and output SST files do not overlap. The same SST file cannot belong to two compactions.

An L0-to-base-level compaction can also use **subcompactions**. RocksDB divides a large key range into smaller ranges and processes them in parallel. TiKV derives the available background jobs from the CPU quota and limits the number of subcompactions; the configured upper bound for its main KV engine is three.

## Compaction Output Files

Compaction must decide where to end each new SST file. TiKV's **compaction guard** keeps this from producing either many tiny files or excessively large files around Region boundaries.

For the usual `default` and `write` column families, the guard avoids cutting an output file below 8 MiB when possible and aims to keep output files around 128 MiB. The exact sizes are configuration choices; the important idea is that Region boundaries influence file cuts without forcing every Region-sized fragment into its own SST file.

These details refine the LSM tree model rather than replacing it. The core path remains: ordered WAL append, ordered memtable, flush to SST, then compaction across levels.
