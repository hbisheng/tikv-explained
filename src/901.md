# RAFTSTORE 901: Raft Peer Lifecycle

## Prerequisites

This chapter builds on the following chapters:

- [RAFT 602: Replica Movement](602.md) introduced creating and removing replicas.
- [RAFT 603: Raft Snapshot](603.md) and [RAFTSTORE 703: Region Worker](703.md) followed snapshot transfer and application.
- [RAFTSTORE 604: Region Split](604.md) and [RAFTSTORE 801: Region Merge](801.md) covered the normal split and merge paths.

This chapter looks at what those paths leave behind when they are interrupted. A Raftstore `PeerFsm` is in memory, so a restart discards it. TiKV instead records enough durable peer state to rebuild the peer or resume the unfinished operation.

## Durable Peer Records

One peer has persistent state in two engines:

| Engine | Record | Purpose |
|---|---|---|
| Raft engine | `RaftLocalState` | Raft's durable protocol progress and log state. |
| KV engine | `RaftApplyState` | The latest applied index and log-truncation boundary. |
| KV engine | `RegionLocalState` | The Region range, peer list, and lifecycle state. |

The Raft engine recovers the Raft protocol. The KV-engine records recover the state machine and which Region belongs on this store.

When an applied Raft entry changes user data, TiKV writes the data changes and the new `RaftApplyState.applied_index` in one KV-engine batch. After a restart, the index and the visible data therefore agree: TiKV neither reapplies a completed entry nor skips one whose data was missing.

`RegionLocalState` is the durable lifecycle marker:

| State | Meaning after restart |
|---|---|
| `Normal` | Recreate an ordinary serving peer. |
| `Applying` | Resume the received snapshot before the peer can serve. |
| `Tombstone` | Do not recreate the removed peer. |
| `Merging` | Recreate the peer with its saved merge context. |

`Tombstone` retains the removed Region's peer identity and epoch. An old Raft message therefore cannot create that removed peer again.

## Restart Begins From These Records

During startup, Raftstore scans `RegionLocalState` and reconstructs the current in-memory peers from it:

- A `Normal` peer becomes a new `PeerFsm`.
- An `Applying` peer recovers the Raft state required by its snapshot, then reschedules snapshot application.
- A `Tombstone` peer is not recreated; TiKV clears its stale Raft metadata, while its physical data follows the cleanup path from [RAFTSTORE 703](703.md).
- A `Merging` peer becomes a `PeerFsm` with its saved merge state, so it can resume the merge decisions from [RAFTSTORE 801](801.md).

The durable records are thus the source of truth. The in-memory structures are rebuilt from them.

## Adding and Removing a Peer

Consider the replica movement from [RAFT 602](602.md). Region 10 initially has three peers:

```text
Store 1: Peer 101 (leader)
Store 2: Peer 102
Store 3: Peer 103
```

PD decides to add Peer 104 on Store 4. After the configuration change is committed, the existing replicas add Peer 104 to their Region metadata. Store 4, however, still has no local state or data for that peer.

The leader begins sending Raft messages addressed to Peer 104 on Store 4. The first one is usually a heartbeat, although a vote or pre-vote can also arrive first during a leadership change. The outer `RaftMessage` carries the Region range, epoch, and source and target peer identities needed by Store 4 to create the peer.

When Store 4 receives this first Raft message, it creates Peer 104 in memory. At this point, Peer 104 is **uninitialized**: Store 4 knows that the peer should exist and which Region it belongs to, but it has not received the Region's key-value data. Peer 104 must wait for the leader to send a Raft snapshot before it can serve.

Removal also leaves durable evidence. When Peer 104 later applies a configuration change that removes itself, TiKV deletes its apply state and writes a tombstone `RegionLocalState`. For an uninitialized peer, the tombstone records the peer ID explicitly because its incomplete Region metadata may not contain a useful peer list. A stale initial message can then be recognized instead of creating Peer 104 again.

Removal can race with the snapshot that initializes the peer:

- If the snapshot metadata has not been persisted, TiKV can destroy the uninitialized peer directly.
- If the peer has entered `Applying`, TiKV waits for snapshot application to finish before completing destruction. Otherwise, the peer could become tombstone first and then be installed again by the snapshot.

This example explains why TiKV keeps the tombstone. Peer 104 may disappear from memory, but a delayed Raft message can still arrive later. The tombstone tells Store 4 that this particular peer has already been removed and must not be created again.

## A Snapshot Crosses the Engine Boundary

[RAFTSTORE 703: Region Worker](703.md) covered the range cleanup and SST ingestion of a received snapshot. The KV and Raft engines use separate atomic write paths, so snapshot recovery needs a durable handoff between them.

Before asynchronous snapshot application begins, TiKV writes `RegionLocalState` as `Applying` in the KV engine. In the same KV-engine batch, it stores a copy of the snapshot's `RaftLocalState` under `snapshot_raft_state_key`. TiKV then writes the Raft state to the Raft engine:

```text
KV engine:   Applying state + snapshot Raft-state copy
                    |
                    v
Raft engine: snapshot Raft state
                    |
                    v
Region worker: finish data cleanup and SST ingestion
                    |
                    v
KV engine:   Normal state, remove the copy
```

If TiKV restarts after the first step, `Applying` tells startup not to serve the peer. The saved copy lets it repair the Raft-engine state before resuming the snapshot. When the Region worker finishes, it changes the state to `Normal` and removes the copy together.

## A Split Across a Crash

A split creates another durable topology transition. Suppose R10 splits and creates R20. When the split entry is applied, TiKV writes the updated metadata for R10, the new metadata for R20, and their apply progress to the KV engine as one batch.

The crash point determines what startup sees:

| Crash point | Durable state | Recovery |
|---|---|---|
| Split entry not persisted | Only the old R10 | Raft can replicate the split entry again. |
| Entry committed but not applied | Old R10; applied index before the split | Apply the committed split entry. |
| KV batch is being written | RocksDB exposes the old or new batch atomically | See either old R10, or complete R10 and R20 metadata. |
| KV batch finished before the in-memory callback | R10 and R20 metadata exist | Rebuild both peers from `RegionLocalState`. |
| Child Raft state has not been created | R20 KV metadata exists | Construct its initial Raft state from the split index and term. |

The router, range index, and read delegates are rebuilt after these durable changes. A crash after the KV batch but before those in-memory updates does not lose the child Region.

## One Child Peer, Two Creation Paths

A more subtle case combines replica movement, snapshot application, and split.

Suppose a store is being added as Peer 3 of a Region. Before its pre-split snapshot finishes, the Region splits and the child Region has Peer 1003 on this store. Peer 1003 can now appear through two paths:

1. The pre-split snapshot initializes Peer 3. Peer 3 then applies the split entry and creates Peer 1003.
2. A post-split Raft message for Peer 1003 reaches the store first and creates an uninitialized Peer 1003, which waits for its own snapshot.

For a while, the store may therefore have two incomplete paths that claim overlapping data.

`pending_snapshot_regions` reserves the range of a snapshot being applied. The first snapshot to claim the range blocks an overlapping snapshot from starting. If the pre-split snapshot finishes and its split creates the initialized child, a later snapshot for the earlier uninitialized child also fails its Region-metadata check: the durable metadata now describes the complete split child rather than the empty peer that requested that snapshot.

The two paths also compete to create the same in-memory peer. `pending_create_peers` records the expected peer ID and whether split has taken ownership of its creation. Together with the `StoreMeta` lock, this permits only two publication orders:

```text
split publishes the initialized child;
Raft-message creation gives up

or

Raft-message creation publishes an uninitialized child;
split replaces it
```

The unsafe order is the reverse: split publishes an initialized peer, then a delayed Raft-message path overwrites it with an empty shell. The shared creation state prevents that order.

The peer ID matters as well. PD may remove a child peer and later add a new generation with a larger peer ID. A delayed split is allowed to replace only the exact uninitialized peer generation it expected; it cannot overwrite that newer peer.

## When Destruction Races With Split

Now suppose PD removes Peer 1003 while the two creation paths are still active.

- **Destruction wins first.** It persists a tombstone for Peer 1003. When the split is applied, it finds existing durable state and skips creating that child peer.
- **Split wins first.** It marks Peer 1003 as owned by split. Destruction sees that ownership and skips deleting the range. The split creates or replaces the child, which can later discover that it is stale and destroy itself through peer garbage collection.

This is why `pending_create_peers` is more than a duplicate-creation check. It decides which transition owns the peer while split and destruction are crossing threads.

## Peer Garbage Collection

A peer does not always receive the configuration-change entry that removed it. For example, it may have been isolated while the other replicas completed the change.

TiKV has two ways for such a stale peer to discover its state:

- Communication with current replicas shows that its peer ID is no longer in the Region's peer list.
- After missing a leader for a long time, it asks PD whether this peer still belongs to the Region.

Once the peer confirms that it is stale, it runs the same durable destruction path and leaves a tombstone. This eventually cleans up the child in the split-wins case above.

## Merge Recovery

[RAFTSTORE 801](801.md) covered the normal merge flow. For recovery, the important state is the `Merging` `RegionLocalState` written by `PrepareMerge`. It records the target Region and the source log interval beginning at `min_index` and ending at the `PrepareMerge` commit index.

Suppose the merge completes on two stores while one source peer remains behind on a third store. That source still remembers the target Region and target epoch from `PrepareMerge`.

- If the local target peer still has the expected epoch and peer ID, the source waits. The target may still apply `CommitMerge` and consume it through the normal path.
- If the target epoch has advanced past the saved merge point, that target has already moved on. It will not apply this old `CommitMerge`, so the source peer can destroy itself.

The source cannot decide from Region overlap alone. Its durable merge relationship with the target determines whether a future `CommitMerge` may still need it.

## Merge and Snapshot Race

A lagging target peer may be unable to apply `CommitMerge` from its local log and instead receive a newer snapshot. That snapshot can represent state from before or after the merge.

For the **expected target peer generation**, the snapshot's Region epoch distinguishes the cases:

- A pre-merge snapshot does not prove that the merge finished, so TiKV must keep the source peer.
- A post-merge snapshot has a Region version beyond the saved target version. TiKV can remove the source and install the target snapshot.

These two metadata changes must appear atomically. Once the source is destroyed, its retained logs can no longer help `CommitMerge`; exposing that destruction before the target snapshot is installed would leave an invalid topology. `atomic_snap_regions` holds the source removals until TiKV can persist them together with the target snapshot state.

The decision changes when the target peer has a **newer generation**, identified by a larger peer ID. The outstanding merge referred to the old target peer. TiKV no longer has to preserve the source for that old relationship, so it can destroy the source before applying the new target peer's snapshot.

## Consecutive Merges

A Region may repeatedly act as a merge target. Becoming a merge source is different because the Region is about to disappear. Before proposing `PrepareMerge`, TiKV checks the progress reported by every peer and inspects the relevant Raft-log interval.

If that interval contains an earlier `CommitMerge`, configuration change, split, or another administrative command that changes the Region's history, TiKV delays the new merge. The peers may not have applied all of that history yet, but they must first replicate it and report it committed.

Raft then supplies the final ordering rule. A peer applies entries in log order, so it must apply an earlier `CommitMerge` before the later `PrepareMerge` that makes the Region disappear. TiKV only needs to persist the current merge state rather than an arbitrary chain of old merge states because it refuses to begin the next disappearance until the preceding topology history is stable across the peers.

---

The earlier chapters followed replica movement, snapshots, splits, and merges in their normal order. Peer lifecycle becomes difficult when those paths overlap or stop halfway. TiKV handles that difficulty with the same foundation throughout: persist enough identity and progress to distinguish old work from current work, then use narrow in-memory guards to decide which concurrent transition may publish the next durable state.
