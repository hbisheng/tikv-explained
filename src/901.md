# RAFTSTORE 901: Raft Peer Lifecycle

[RAFT 602: Replica Movement](602.md) introduced creating and removing replicas. [RAFT 603: Raft Snapshot](603.md) and [RAFTSTORE 703: Region Worker](703.md) followed snapshot transfer and application. [RAFTSTORE 604: Region Split](604.md) and [RAFTSTORE 801: Region Merge](801.md) covered the normal split and merge paths.

This chapter looks at what those paths leave behind when they are interrupted. A Raftstore `PeerFsm` is in memory, so a restart discards it. TiKV instead records enough durable peer state to rebuild the peer or resume the unfinished operation.

## Durable Peer Records

One peer has persistent state in two engines:

| Engine | Record | Purpose |
|---|---|---|
| Raft engine | `RaftLocalState` | Raft's durable protocol progress and log state. |
| KV engine | `RaftApplyState` | The latest applied index and log-truncation boundary. |
| KV engine | `RegionLocalState` | The Region range, peer list, and lifecycle state. |

The Raft engine recovers the Raft protocol. The KV-engine records recover the state machine and which Region belongs on this store.

When an applied Raft entry changes user data, TiKV writes the data changes and the new `RaftApplyState.applied_index` in one KV-engine batch. After a restart, the index and the visible data therefore agree: TiKV neither reapplies a completed entry nor skips one whose data was missing.

`RegionLocalState` is the durable lifecycle marker:

| State | Meaning after restart |
|---|---|
| `Normal` | Recreate an ordinary serving peer. |
| `Applying` | Resume the received snapshot before the peer can serve. |
| `Tombstone` | Do not recreate the removed peer. |
| `Merging` | Recreate the peer with its saved merge context. |

`Tombstone` retains the removed Region's peer identity and epoch. An old Raft message therefore cannot create that removed peer again.

## Restart Begins From These Records

During startup, Raftstore scans `RegionLocalState` and reconstructs the current in-memory peers from it:

- A `Normal` peer becomes a new `PeerFsm`.
- An `Applying` peer recovers the Raft state required by its snapshot, then reschedules snapshot application.
- A `Tombstone` peer is not recreated; TiKV clears its stale Raft metadata, while its physical data follows the cleanup path from [RAFTSTORE 703](703.md).
- A `Merging` peer becomes a `PeerFsm` with its saved merge state, so it can resume the merge decisions from [RAFTSTORE 801](801.md).

The durable records are thus the source of truth. The in-memory structures are rebuilt from them.

## A Snapshot Crosses the Engine Boundary

[RAFTSTORE 703: Region Worker](703.md) covered the range cleanup and SST ingestion of a received snapshot. The KV and Raft engines use separate atomic write paths, so snapshot recovery needs a durable handoff between them.

Before asynchronous snapshot application begins, TiKV writes `RegionLocalState` as `Applying` in the KV engine. In the same KV-engine batch, it stores a copy of the snapshot's `RaftLocalState` under `snapshot_raft_state_key`. TiKV then writes the Raft state to the Raft engine:

```text
KV engine:   Applying state + snapshot Raft-state copy
                    |
                    v
Raft engine: snapshot Raft state
                    |
                    v
Region worker: finish data cleanup and SST ingestion
                    |
                    v
KV engine:   Normal state, remove the copy
```

If TiKV restarts after the first step, `Applying` tells startup not to serve the peer. The saved copy lets it repair the Raft-engine state before resuming the snapshot. When the Region worker finishes, it changes the state to `Normal` and removes the copy together.

## Short-Lived Guards for Concurrent Changes

The durable state handles restart. While TiKV is running, a split, an initial Raft message, a snapshot, and peer destruction can overlap. Raftstore uses three in-memory guards to give each transition one owner:

- `pending_snapshot_regions` reserves a key range while a snapshot is pending, so an overlapping snapshot cannot begin.
- `pending_create_peers` reserves creation of a Region peer. It prevents an initial message from creating an uninitialized peer while a split is creating that same child peer.
- `atomic_snap_regions` holds the overlapping source-peer removals needed by a merge-related snapshot until TiKV can publish the target snapshot state and those removals as one KV-engine update.

These guards resolve concurrent work in the current process. After a restart, TiKV recreates them as work arrives, while the durable peer records determine what work is resumed.

## Merge Recovery

The normal merge protocol is already covered in [RAFTSTORE 801: Region Merge](801.md). Its recovery record is the `Merging` `RegionLocalState` written by `PrepareMerge`. It identifies the target Region and saves the source's merge progress.

On restart, TiKV restores that record into the source peer. If the local target still has the expected Region epoch and peer ID, the normal merge coordination can continue. If the target's epoch has advanced or its peer ID has changed, the target has moved past this merge point and the old source peer can be destroyed.

This same identity check also governs a racing target snapshot. A snapshot for the expected target peer is coordinated with removal of the source peer; a newer target peer no longer has an outstanding relationship with that source.

---

The earlier chapters establish what replica movement, snapshots, splits, and merges do during normal execution. This chapter establishes the recovery rule behind all of them: first make the lifecycle transition durable, then rebuild or resume from that durable record. In-memory guards prevent conflicting transitions while the store is running; recovery takes its direction from the durable records.
